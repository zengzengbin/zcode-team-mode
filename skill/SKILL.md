# ZCode 小队模式

本技能仅适用于 ZCode。由当前主 Agent 分解任务、分派工作并最终验收；不改变主 Agent 的模型。各角色的模型与思考强度在安装时通过交互初始化绑定（后续支持随时调整），执行时不使用 fast，不根据主 Agent 随意换模型，也不在未获授权时自动降级。

| Agent 类型 | 模型 | 思考强度 | 用途 |
|---|---|---|---|
| `team-explorer` | `<EXPLORER_MODEL>` | `<EXPLORER_THOUGHT_LEVEL>` | 只读定位大型代码库的文件、入口、调用关系 |
| `team-executor` | `<EXECUTOR_MODEL>` | `<EXECUTOR_THOUGHT_LEVEL>` | 在明确的文件归属内实现、修改和验证 |
| `team-reviewer` | `<REVIEWER_MODEL>` | `<REVIEWER_THOUGHT_LEVEL>` | 独立评审稳定产物，提供有证据的问题 |
| `team-expert-advisor` | `<EXPERT_ADVISOR_MODEL>` | `<EXPERT_ADVISOR_THOUGHT_LEVEL>` | 复杂决策、疑难问题、建模或受委派的复杂执行 |

## 启用与退出

用户在消息中单独一行输入以下任一开启口令（不必是第一行），任务写在口令行之外的其他行：

```text
$zcode-team-mode
```

```text
开启 ZCode 小队模式
```

开启口令接受 `开启`、`打开`、`启动` 三种说法，`ZCode` 一词可省略（`开启小队模式`、`打开 ZCode 小队模式` 均可），也接受口令独占一行写成 `使用 $zcode-team-mode`；口令对大小写和半角/全角空格不敏感（`开启Zcode小队模式` 也可），但必须独占一行，句子中间提到口令不算。从 `$` 补全菜单选中本技能同样算显式启用：ZCode 会把它渲染成指向本技能 SKILL.md 的 Markdown 链接，该链接只要位于任一行的行首（其后可并列其他技能链接与任务文字）即按启用处理，句子中间引用的链接不算。除上述形式外，只包含解释、询问或其他文字的行不会启用。仅当本轮 hook 附加上下文明确给出 `ZCODE_TEAM_MODE=active` 时按小队规则派发。只是读取本文件或自动加载技能不能启用模式；缺少 hook 确认时说明未启用，不冒充已生效。

已成功启用时（本轮口令触发开启，且 hook 确认 `ZCODE_TEAM_MODE=active`），该条回复必须包含一行 `👾 已开启小队模式`，再继续处理任务。仅当轮输出一次；hook 持续 active 的后续回复不重复输出该行（hook 会显式说明此前已输出）；未启用或 hook 未确认时不得输出，也不冒充已生效。上下文压缩后本条约束依然有效：没有 hook 的开启确认就不得补输出。

启用后，当前聊天的后续任务都继续使用小队规则，直到用户在消息第一行明确输入：

```text
退出 ZCode 小队模式
```

退出口令接受 `退出`、`关闭` 两种说法（`退出小队模式`、`关闭 ZCode 小队模式` 均可，大小写与空格不敏感），同样独占一行、不必是第一行。已成功退出时（本轮口令触发退出，且 hook 返回 `ZCODE_TEAM_MODE=inactive`），该条回复必须包含一行 `👾 已关闭小队模式`，再继续处理任务，与开启时的 `👾 已开启小队模式` 对称；仅当轮输出一次，hook 保持 inactive 的后续回复不重复输出该行。

任务完成、普通回复结束或新一轮消息不自动退出。`查看 ZCode 小队状态`（另有 `查看小队状态`、`查看小队模式`、`查询小队状态` 等写法）可查询当前聊天状态，同样独占一行、任意位置。口令须直接独占一行，引用、代码块、附件里的口令不执行。退出确认后，本文件的小队派发限制不再适用。其他聊天单独管理。

## 派发

1. 简单问题或主 Agent 能直接完成的短任务直接处理。只有独立子任务确有收益时才派发；一个问题默认一个成员，不凑满四种角色，独立工作才并行。
2. 使用 ZCode 原生 `Agent`（或其 `Task` 别名），显式填写 `subagent_type`。启用期间只禁止内置 `general-purpose`、`Explore` 和省略类型，以及通过命令行另开代理绕过限制；四个 team-* 角色与文档/浏览器类专用 agent（如各 `*-visual-judge`、`image-generator`）等其他专用角色照常按需派发。其他普通技能仍可按任务加载。
3. 每次交办写清问题或交付物、必要背景、范围、验收依据及写权限。执行任务必须有唯一文件/模块负责人；成员共享工作区，不得撤销他人修改。主 Agent 负责跨任务决策与整合。
4. 给 Explorer、Reviewer、ExpertAdvisor 独立、精简的任务说明，提供原始证据和用户约束，把怀疑当线索而非结论。ZCode 原生子 Agent 有独立任务上下文，任务说明之外的对话历史不自动传递（派发参数无历史继承开关，详见派发「上下文分档」）。
5. 小队成员不得继续派发子 Agent；需要协作时向主 Agent 回报。探索/评审成员没有写入或 shell 工具；执行/专家只能在主 Agent 明确的授权范围内工作。需要运行测试的评审应让主 Agent 提供结果或派 Executor，不假装自己运行过。
6. ExpertAdvisor 固定为已配置的专家模型与强度（如 `<EXPERT_ADVISOR_MODEL> + <EXPERT_ADVISOR_THOUGHT_LEVEL>`，安装时由用户指定并可调整）。它表示职责，不承诺一定比主模型更强。默认交付分析与建议；主 Agent 可明确交办建模、自动化或实现，须给写入范围。
7. 模型不可用、强度不被接受、角色缺失或 hook 报错时，报告具体缺口，不改用内置角色、不悄悄换模型或降低强度。主 Agent 可以继续授权范围内的独立工作；缺失的独立评审必须如实说明。
8. 等待已派发的任务结束并核验结果后再交付。只复用同一成员的直接续做；独立评审用新的任务说明。是否做评审由风险和用户需求决定，不因改动行数机械扩队。

### 上下文分档

子 Agent 只有任务说明带来的上下文，拿不到父会话对话历史；任务说明之外不自动继承。派发时按信息密度选一档，任务说明的详细程度随之升级：

| 档位 | 适用场景 | 任务说明必含 |
|---|---|---|
| 轻量 | 目标单一、文件与验收标准都明确，不需要近期决策 | 目标、范围（文件/模块）、验收依据、写权限 |
| 中等 | 结论散落在近期对话里，简短说明容易遗漏或让成员做出相反选择 | 轻量全部 + 「已定决策」摘要（如：缓存走 SQLite 不用 Redis；接口保持 v2 签名），逐条写清结论与生效范围 |
| 完整 | 背景跨度大、证据链长，摘要会失真 | 中等全部 + 证据文件路径（把关键材料整理成文件放进工作区，让成员自己读），不要粘贴大段原文 |

跨成员传递结论时同样按此办理：A 成员发现的背景要由主 Agent 转述进 B 的任务说明，不指望成员之间共享认知。需要完整对话历史时没有派发级开关，只能落成证据文件或另开会话，不要假称能继承。

## 评审与收尾

评审稳定的修改及相关需求，不扩大为全库清理。报告具体位置、可复现影响和建议；无实质问题时明确说未发现。主 Agent 决定采纳哪些建议，实施后按影响验证。评审后相关文件又改变时，需要补充检查变更部分。区分静态校验、工具运行和真实使用验收。

关于 hook 生效范围、安装路径、故障边界及维护，按需阅读 [运行机制](references/runtime.md)。
